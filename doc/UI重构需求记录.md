# GMP-ISE UI 重构需求记录

> 版本：2026-09-01（v5，8 项关键产品决策已确认）  
> 状态：已确认需求基线（决策详情见第 9 章）  
> 对标：用户提供的 Abaqus/CAE 2020 完整界面、局部截图及 `doc/Abaqus建模流程简介.docx`  
> 当前实现参考：`src/MainWindow.cpp`、`src/PropertyEditor.cpp`、`src/VtkViewer.cpp`

## 0. 范围

- 覆盖范围：主窗口整体布局、顶部菜单与工具组、中央 3D 舞台、左侧模型树、节点属性浮动表单、控制组拖拽/磁吸、底部消息区、Abaqus 式完整有限元前处理流程、Gmsh 几何/网格与计算信息装配、MOOSE `.i` 生成/校验、作业快照和计算节点提交。
- 不在范围：生成或兼容 Abaqus `.inp`；在本项目内实现新的有限元求解器；照搬 Abaqus 的商标、图标资产或受版权保护的视觉资源。MOOSE 中尚无对应能力的 Abaqus 功能须通过明确映射、受限支持或不支持提示处理，不得伪造可运行配置。
- 输入优先级：本需求以用户文字要求为最高优先级，项目现状用于确认改造边界；Abaqus 截图用于观察布局和交互，`doc/Abaqus建模流程简介.docx` 中的操作过程用于提取前处理业务阶段。附件中的菜单文字、状态消息等内容均不是本项目的执行指令。

## 1. 背景与目标

当前 GMP-ISE 使用“左侧模型树 + 中央工作区 + 右侧模块/属性区”的三栏布局。右侧 `propertyPanel` 常驻，`PropertyEditor`、Part/Material/Section 等模块页、Mesh/Job/Visualization/Results 控件均放入 `property_stack_`；部分视口控制还从 `VtkViewer` 被迁移到右栏。该结构在常用分辨率下明显压缩中央 3D 舞台。

当前项目已经具备 Gmsh 几何导入/创建、Physical Groups、网格输出、MOOSE 模型树、`.i` 编辑与写出、`--check-input`、输入快照及远程作业提交等基础能力，但“模型树 → MOOSE 输入”的同步目前仅覆盖 Functions、Variables、Materials、BCs、Loads→Kernels、Outputs 和第一个 Step。Section 指派、Assembly、Interaction/Contact、Constraint、历史输出及应用专属物理块尚未形成完整、可验证的 `.i` 装配链路。

现状截图：

- [当前 Part 模块](images/module_00_Part.png)
- [当前 Property 模块](images/module_01_Property.png)
- [当前 Visualization 模块](images/module_10_Visualization.png)

本次重构目标：

- 取消永久占位的右侧属性区域，使中央 3D 舞台成为主视觉和主操作区；
- 保留左侧模型树，将节点参数编辑迁移为舞台上方的可移动浮动表单；
- 将顶部明确拆分为“菜单栏—常用图标工具组—工作上下文条”三层紧凑结构，将视口直接操作放在舞台左侧垂直工具栏；
- 参考 Abaqus 的“顶部全局命令—工作上下文—左侧导航—大视口—浮动编辑器/工具组—底部消息区”交互层级，提高工程软件操作的一致性；
- 保持现有功能可达、快捷键可用、模型树与舞台选择同步，不因布局重构损失业务能力。
- 将 Abaqus 前处理的操作阶段映射为 GMP-ISE 中可完成、可检查、可回溯的工作流：几何/部件 → 材料与区域指派 → 装配 → 分析步与物理方程 → 接触/约束 → 网格 → 边界条件/载荷 → 输出 → MOOSE 输入 → 作业提交。
- 以“生成计算节点可直接运行的 MOOSE `.i` 和配套网格包”为最终完成标准；正常流程不要求用户手工修补生成后的 `.i`。

### 1.1 最终产品目标

本次 UI 重构不是单纯换肤，最终应交付一条闭环：

```text
Gmsh .geo / OCC 几何 / 导入 CAD
        ↓ 几何同步、装配定位、Physical Groups
      Gmsh .msh
        + 材料/变量/物理方程/区域指派
        + Step/Executioner/求解控制
        + BC/Load/Function
        + Contact/Constraint/Interaction
        + Field/History Output
        ↓ MOOSE 输入装配与校验
      case.i + mesh.msh + extra files + manifest.json
        ↓ 现有作业系统
      计算节点运行 MOOSE
        ↓
      Exodus/CSV/日志 → Results/Visualization
```

说明：`.geo` 是几何、网格控制和 Physical Groups 的来源之一，不应把 `.geo` 文本直接粘贴进 `.i`。标准链路是先由 Gmsh 生成保留命名物理组的 `.msh`，再由 `.i` 的 `[Mesh]`/`FileMesh` 引用网格文件，并将其他计算信息装配为相应 MOOSE blocks。

## 2. 对标结论与目标布局

### 2.1 当前界面与 Abaqus 对标差异

| 维度 | GMP-ISE 当前状态 | 目标状态 |
|---|---|---|
| 主工作区 | 左、中、右三栏常驻，右栏约占 20% 宽度 | 左侧树常驻，中央舞台占满其余宽度，无永久右栏 |
| 模块切换 | 顶部 13 个等宽页签，占用整行 | 工作上下文条使用紧凑“模块”选择器，当前模型和活动对象在同一行显示 |

| 视口命令 | 部分控件在中央上方，部分被迁入右栏 | 高频按钮吸附在舞台左侧；高级设置以浮动组或弹窗打开 |
| 属性编辑 | 右侧 `PropertyEditor` 常驻并随树选择刷新 | 单击节点只选择和定位；双击或执行“编辑”后打开事务式模态表单 |
| 舞台占比 | 中央被右栏、顶部控制行和底部控制区共同挤压 | 舞台为主，非必要区域默认紧凑或折叠 |
| 状态反馈 | 状态栏 + 常驻底部 Console | 保留状态栏；消息/作业区默认紧凑，可展开查看详情 |

### 2.4 Abaqus 前处理流程与 GMP-ISE/MOOSE 映射

`doc/Abaqus建模流程简介.docx` 共 22 页、44 张操作截图，展示了一个“混凝土立方体 + 钢板”的完整建模和提交准备过程。原始操作截图已提取至 `doc/images/abaqus-workflow/`，可在[第 10 章“操作对标图附录”](#10-abaqus-操作对标图附录)逐步查阅。其业务阶段映射如下：

| Abaqus 阶段 | 文档中的主要操作 | GMP-ISE/MOOSE 目标映射 |
|---|---|---|
| Part / Sketch | 创建实体、绘制矩形、尺寸约束、拉伸，形成混凝土块和钢板 | Sketch/Part/Feature + OCC/Gmsh 几何；保存可重建参数和几何来源 |
| Property / Material | 定义混凝土与钢材本构参数 | Materials 节点 + MOOSE 材料/本构模板；参数随选定 MOOSE 应用和物理系统变化 |
| Section / Assignment | 创建实体截面并把材料指派给几何区域 | Section 作为“材料—Physical Volume/Subdomain 绑定”；生成时转换为 `block`/子域限制，不直接输出无效 `[Sections]` |
| Assembly | 创建实例并平移到接触位置 | Assembly/Instance 节点记录部件引用与变换；变换必须在 Gmsh 网格生成前落实到最终几何 |
| Step | 创建静力通用分析步，设置时间、增量和非线性参数 | Physics/Kernels + Executioner + Solver/Preconditioning 配置；Step 不是仅改时间参数 |
| Field Output | 选择应力、应变、位移、损伤等场变量 | Outputs 中的 Exodus 变量选择，以及所需 AuxVariables/AuxKernels |
| History Output | 选择参考点位移与反力等历史量 | Postprocessors/VectorPostprocessors + CSV/Exodus 输出 |
| Reference Point / Coupling | 创建参考点并将顶面运动耦合到参考点 | Constraints/受限运动映射；仅在目标 MOOSE 应用支持时生成对应对象 |
| Interaction / Contact | 定义摩擦系数和面—面接触 | Contact/Constraints/InterfaceKernels 等应用专属模板；主从面由 Physical Surfaces 绑定 |
| Set | 建立节点/面集合供输出和约束引用 | Gmsh Physical Groups 或项目选择集；生成前解析为稳定的 boundary/block 名称 |
| Mesh | 对两个部件划分网格 | Gmsh `.geo`/OCC → `.msh`；保留 Physical Groups、单元类型、维度和质量摘要 |
| BC / Load | 固定底面，在钢板/参考点施加位移 | MOOSE BCs/Functions/应用专属边界算子；绑定到命名 boundary 或参考对象 |
| Job | 创建计算作业并写出 Abaqus 输入 | 生成 `case.i + mesh.msh + manifest.json`，通过现有作业系统提交到计算节点 |

映射原则：Abaqus 的模块名称只用于表达用户工作阶段，MOOSE `.i` 必须遵循所选 MOOSE 应用的真实 block 和参数契约。不存在一一对应关系时，UI 必须要求用户选择受支持的 MOOSE 模板或明确提示“不支持”，不得按 Abaqus 名称直接拼接伪 block。

## 3. 需求分解

### REQ-001 取消右侧属性区域并放大中央舞台（P0）

- 目标/价值：移除无论是否编辑都占宽的右栏，让几何、网格和结果成为默认最大可视内容。
- 业务规则：
  - 主水平布局由三栏改为“左侧模型树 + 中央舞台”两栏；不得保留空白占位或隐藏后仍参与布局计算的右侧 `propertyPanel`。
  - 中央舞台占满模型树以外的全部可用宽度；浮动窗口和浮动工具组不得改变舞台布局尺寸。
  - 左侧模型树默认宽度建议为 240～300 px，可拖动调整；最窄状态须保留图标/树层级和横向滚动能力。
  - 底部 Console/作业消息区默认采用紧凑高度或折叠状态，用户需要时可展开；状态栏继续常驻。
  - 窗口尺寸、左栏宽度、底部区展开状态在下次启动时恢复。
- 数据/接口影响：不修改模型树节点和 `params` 数据结构，仅调整控件承载方式和界面状态存储。
- 关联逻辑/路径：`src/MainWindow.cpp` 中 `main_split`、`property_panel`、`property_stack_`、`vertical_split`。
- 验收标准：
  - 启动后主窗口无永久右侧栏，左树右边直接连接中央舞台。
  - 在 1440×900 内容区下，左树使用默认宽度时，中央工作区宽度不低于主内容区的 75%。
  - 关闭所有浮动窗口后，舞台不会留下空白占位；缩放主窗口时舞台优先获得新增空间。

### REQ-002 建立舞台左侧垂直工具栏（P0）

- 目标/价值：将与中央舞台直接相关的操作放到指针移动距离最短的位置，并与 Abaqus 视口左侧工具条保持一致的操作习惯。
- 业务规则：
  - 工具栏吸附在中央工作区的舞台左缘，垂直排列，呈紧凑窄条；可采用舞台覆盖层或窄停靠条实现，但不得形成新的大面积侧栏。
  - 默认宽度建议为 32～48 px，只显示图标和分隔线；需要参数填写的命令必须打开弹窗，不得直接把表单扩展在垂直工具栏中。
  - 高频功能至少覆盖：选择模式、框选、旋转、平移、缩放、适配窗口、标准视图/轴测图、显示模式、显示/隐藏/隔离、剖切，以及当前已有的草图 2D 编辑工具。
  - 按“选择与导航 / 视图与显示 / 分析与测量 / 当前模块工具”分组，组间使用间隔或分隔线，不把所有按钮堆成一个无层次长列。
  - 工具栏随工作上下文切换：通用导航按钮常驻，Sketch/Mesh/Visualization 等模块只显示本模块相关组。
  - 按钮使用图标为主，悬停提示须包含功能名和快捷键；激活中的互斥工具必须有明确选中态，禁用态须可辨识。
  - 工具栏遮挡内容时允许折叠为单个展开按钮；小窗口下允许分段折叠或滚动，不允许把舞台挤出可视区。
- 关联逻辑/路径：`src/VtkViewer.cpp`、`include/gmp/VtkViewer.h`、`src/SketchPanel.cpp`、`src/MainWindow.cpp` 中 Visualization 控件迁移逻辑。
- 验收标准：
  - 用户无需进入右侧区域即可完成视角调整、适配、选择及主要显示操作。
  - 切换工具时状态与实际 VTK 交互模式一致；按 `Esc` 可退出当前临时工具并返回默认选择模式。
  - 工具栏展开、收起或切换模块时，VTK 场景不得出现明显尺寸跳动；若采用窄停靠条，其宽度变化必须受控且不随模块任意改变。

### REQ-003 重构顶部菜单、图标工具组和工作上下文条（P0）

- 目标/价值：形成稳定的全局命令入口，减少宽页签和重复文字按钮对垂直空间的消耗。
- 业务规则：
  - 顶部保留标准菜单区，按工程软件习惯组织 File、Model、View、Mesh、Job、Tools、Settings、Help 等菜单；现有命令不得因改组而丢失。
  - 菜单下方为多个紧凑常用图标工具组；工作上下文条位于工具组下方，不与工具按钮混成同一行。
  - 现有 13 个等宽模块页签改为工作上下文条中的“模块”紧凑选择器；模块切换后，只刷新与该模块有关的命令组和舞台工具。
  - “工作上下文条”用于定义后续命令的工作模式和作用目标，不是新的业务面板，也不承载参数表单。
  - 工作上下文条包含以下字段：
    - 模块：可主动切换 Sketch、Part、Material、Mesh、Job、Visualization、Results 等工作模式；
    - 当前模型/项目：显示命令所属项目或模型；单模型阶段默认只读，多模型能力出现后再启用下拉选择；
    - 当前对象：显示当前 Part、Sketch、Material、Mesh、Job 或 Result 等上下文对象，选项随模块动态变化，并与模型树选择同步。
  - 当前对象不存在时明确显示“未选择”；不适用于当前模块的字段隐藏或禁用，不保留没有含义的空白输入框。
  - 工作上下文条不重复展示完整树路径；完整层级仍由左侧模型树承担。
  - 常用功能按钮以图标为主，包括新建、打开、保存、撤销/重做、同步模型、生成/预览网格、检查、运行、停止等；文字说明通过 Tooltip 和菜单项提供。
  - 菜单项、快捷键、工具栏按钮应复用同一 `QAction` 或同一命令源，启用/禁用、选中状态和执行结果保持一致。
  - 高频命令按“项目 / 编辑 / 建模 / 网格 / 作业”分成多个可独立移动的按钮组。
- 关联逻辑/路径：`src/MainWindow.cpp` 中 `build_menu()`、`build_toolbar()`、`module_tabs_`、`module_toolbar_actions`。
- 验收标准：
  - 所有现有菜单与工具栏命令均可从新界面到达，原快捷键继续生效。
  - 除操作系统标题栏外，顶部按“菜单栏 + 图标工具组 + 工作上下文条”三层显示；三层均使用紧凑高度，合计建议控制在 80～100 px。
  - 1280 px 宽度下允许工具组进入溢出菜单，但工作上下文的关键字段和舞台不得被挤至不可用。
  - 切换模块后，工作上下文、工具组、树选中项和舞台模式保持同步；用户始终能判断命令将作用于哪个对象。

### REQ-004 支持工具组拖拽、浮动与磁吸（P0）

- 目标/价值：允许用户按任务习惯布置常用功能，并实现类似 Abaqus 右上角浮动工具组的效果。
- 业务规则：

### REQ-006 用浮动表单替代右侧 PropertyEditor（P0）

- 目标/价值：在不永久占用舞台宽度的前提下，继续提供完整的节点参数查看、编辑和校验能力。
- 业务规则：
  - 属性编辑器以独立、可移动、可缩放的浮动窗口显示在中央舞台之上，默认在舞台中央偏左打开，不依附右侧布局。
  - 当前目标基线采用接近 Abaqus 的模态编辑方式：编辑窗口打开期间阻止任何会改变活动对象的树操作，但允许窗口移动，以便用户查看未被遮挡的舞台内容。
  - 窗口标题包含动作和对象名称，例如“编辑材料 — Material-1”；表单继续承载 General、Parameters、Preview 以及现有快捷参数、高级参数和校验汇总能力。
  - 节点创建/编辑弹窗底部默认提供“确定 / 取消”；“确定”通过校验后一次性写回并关闭，“取消”放弃本次全部改动。确有连续调参需求的表单可追加“应用”，但不得成为所有弹窗的强制按钮。
  - 日志、结果详情和纯查看类窗口可以保持非模态；它们不得与节点编辑弹窗混用相同的提交语义。
  - Sketch 2D 编辑器属于需要持续操作中央舞台的交互工作窗，不套用普通属性表单的模态阻断规则；它以非模态浮动工作窗显示绘图、约束和尺寸工具，关闭或“完成编辑”时保存并退出 2D 会话。
  - 表单字段根据节点类型组织成分组或页签，默认聚焦首个可编辑字段；校验失败时阻止提交并将焦点定位到首个错误字段。
  - 弹窗内容必须针对工作窗重新排版，不得直接保留旧右侧窄栏的纵向堆叠结构；默认尺寸内应直接显示当前功能的主要字段、主操作和底部确认区。
  - 同一弹窗不得出现外层与内容层并存的双竖向滚动条。复杂功能优先按任务分组或页签拆分；确需滚动时只允许保留一层内容滚动，并固定关键操作区。
  - 记忆各类型表单的合理尺寸；节点编辑弹窗每次须校验位置，当上次位置越界时在当前舞台内重新居中。浮动窗口不得默认遮住整个几何区域。
  - 关闭浮动表单不改变树选择和舞台显示；删除正在编辑的节点前必须关闭表单或完成删除确认。
- 数据/接口影响：现有 `PropertyEditor` 的节点读取、快捷表单、参数同步、验证和预览逻辑继续复用；需要增加编辑缓冲或快照，以支持确定/取消及可选应用语义。
- 关联逻辑/路径：`src/PropertyEditor.cpp`、`include/gmp/PropertyEditor.h`、`src/MainWindow.cpp` 中 `property_editor_->set_item(...)` 调用点。
- 验收标准：
  - Materials、Sections、Steps、BC、Loads 的快捷表单，以及其他节点的高级参数表均可在浮动窗口完成编辑。
  - 未点击“确定”（或可选“应用”）的修改在取消后不写入模型树，不标记项目为已修改。
  - 模态编辑窗打开时不能切换活动节点；关闭后树、工作上下文条和舞台仍指向原对象。

### REQ-012 建立 Gmsh 几何、Physical Groups 与 MOOSE 网格契约（P0）

- 目标/价值：明确 `.geo` 如何进入最终计算案例，保证几何选择能够稳定成为 MOOSE 的 block/boundary 语义。
- 业务规则：
  - 几何来源可以是 `.geo/.geo_unrolled`、OCC 特征历史、STEP/IGES/BREP 或项目内基元；所有来源在生成网格前统一同步到 Gmsh 模型。
  - Assembly 中的实例变换、布尔关系和最终拓扑必须先落实，再创建/刷新 Physical Groups；不得引用变换前已失效的实体 tag。
  - 体、面、线、点选择集使用用户可读且项目内唯一的名称；体组用于 MOOSE block/subdomain，面/线/点组用于 boundary、接触面、约束或输出选择。
  - 生成 `.msh` 后读取并保存物理组清单、维度、名称、实体数量、网格维度、单元类型、单元数和质量摘要；网格节点记录其几何来源版本。
  - 最终 `.i` 使用 `[Mesh] type = FileMesh` 引用随案例打包的 `.msh` 相对路径；不得把 `.geo` 语句直接写入 `.i`。
  - 若 `.geo` 未定义所需物理组、名称冲突、组为空、维度错误或组在重建后失效，必须阻止 `.i` 进入“可提交”状态并定位问题对象。
- 数据/接口影响：Physical Groups 名称成为跨 Gmsh、项目模型、`.i` 和结果的稳定语义键；裸 Gmsh entity tag 仅作为瞬时实现信息。
- 关联逻辑/路径：`src/GmshPanel.cpp`、`include/gmp/GmshPanel.h`、`src/OccBridge.cpp`、Mesh 模型树节点、`MoosePanel::inject_mesh_block()`。
- 验收标准：从 `.geo` 或项目几何生成 `.msh` 后，体组和边界组名称可在材料、BC、Load、Contact、Output 表单中直接选择；导出的 `.i` 引用正确网格文件并通过物理组绑定检查。

### REQ-013 建立前处理对象到 MOOSE blocks 的显式映射（P0）

- 目标/价值：把 Abaqus 式操作语义转换为所选 MOOSE 应用真实可执行的输入，而不是按节点名称机械输出文本。
- 业务规则：
  - 创建计算模型前必须选择“求解应用/物理配置”，至少包含 MOOSE 可执行程序或应用标识、模板版本、空间维度、物理系统和单位约定。
  - 应用以可扩展档案注册，不得把产品锁定到单一可执行程序；档案声明应用/版本、计算环境、能力清单、映射注册表、校验命令、支持级别和求解单位合同。
  - 应用选择为项目级活动配置；切换前生成对象与单位兼容性报告，不兼容对象保留但标记为“未映射/阻断”。每个 Job 固化应用、版本、映射和计算环境快照。
  - 映射层至少覆盖：Variables、Initial Conditions、Kernels/Physics、AuxVariables/AuxKernels、Materials、BCs、Functions、Constraints、Contact/Interface、Executioner、Solver/Preconditioning、Postprocessors、VectorPostprocessors 和 Outputs。
  - Material 表单字段、Load/BC 类型、Contact/Constraint 类型和 Output 变量必须由当前应用模板约束；切换应用时重新校验，不得继续使用另一应用的无效类型。
  - Section 的核心语义是“材料/属性 → Physical Volume/Subdomain 指派”；生成时转换为相关 Material/Physics 对象的 `block` 限制，而不是默认输出 `[Sections]`。
  - Load 根据物理类型映射到 Kernel、BC、Function、Postprocessor 或应用专属对象，不得统一按 `BodyForce` 输出。
  - Step 同时约束物理求解阶段、Executioner、时间/增量、非线性和线性求解配置；多 Step 若目标应用不支持串联执行，必须明确提示并阻止静默只取第一个。
  - Interaction、Contact、Coupling 等只有在当前应用模板声明支持时才允许生成；否则保留对象但标记为“不支持生成”。
- 数据/接口影响：需要版本化的 MOOSE 类型/参数映射注册表，表单、校验器和 `.i` 生成器共用同一份定义。
- 关联逻辑/路径：`src/PropertyEditor.cpp`、`src/MainWindow.cpp::default_params_for_kind()`、`build_block_from_root()`、`build_executioner_block()`、`templates/moose/`。
- 验收标准：对已支持模板，UI 对象可以稳定生成目标 blocks；对缺少映射或参数的对象，生成器返回可定位错误，不输出看似完整但不可运行的 `.i`。

### REQ-014 实现确定性的 MOOSE `.i` 装配器（P0）

- 目标/价值：把网格、物理模型和求解配置合并成计算节点可直接使用的输入文件，取代依赖用户手工修补的同步方式。
- 业务规则：
  - 装配输入包括：选定模板/应用、最新有效 `.msh`、Physical Groups、项目模型树对象、求解/并行配置及允许的专家扩展片段。
  - 生成器按稳定顺序输出适用 blocks，至少考虑 `[Mesh]`、`[GlobalParams]`、`[Variables]`、`[ICs]`、`[Kernels]`/`[Physics]`、`[AuxVariables]`、`[AuxKernels]`、`[Materials]`、`[BCs]`、`[Constraints]`、`[Executioner]`、`[Preconditioning]`、`[Postprocessors]`、`[VectorPostprocessors]`、`[Outputs]`。
  - 仅输出当前应用真实支持且实际需要的 blocks；block 名、对象类型、参数名、枚举和值格式由映射注册表决定。
  - 同一项目状态重复生成应得到语义和文本均稳定的结果；对象顺序、空白和命名不得随机漂移。
  - 路径在案例包内使用安全相对路径；含空格或特殊字符的值按 MOOSE 输入规则正确引用。
  - 生成界面提供来源追踪：每个 block/对象可以定位回模型树节点、Physical Group 和模板版本。
  - 默认生成区由系统管理；若允许专家自定义，必须使用明确的扩展区或覆盖机制，并在重新生成时提供差异预览，不能静默覆盖用户文本。
  - 普通模式下生成 `.i` 只读；专家模式使用与系统生成区分离的受控 Custom Objects/Blocks 扩展层。完全手工模式必须显式生成脱离结构化同步的独立副本，返回结构化模式时生成新文件并展示差异。
  - 正常前处理流程完成后，用户无需删除多余 `type`、补写 Mesh、替换占位 boundary 或手工修改其他生成块。
- 数据/接口影响：现有 `sync_model_to_input()` 和 `MoosePanel::apply_model_blocks()` 需升级为结构化装配服务，避免用正则整段替换作为唯一生成机制。
- 关联逻辑/路径：`src/MainWindow.cpp::sync_model_to_input()`、`src/MoosePanel.cpp::apply_model_blocks()`、`upsert_block()`、`inject_mesh_block()`、`templates/moose/`。
- 验收标准：参考案例在相同项目状态下连续生成两次无非预期差异；输出 `.i` 不含占位路径、空 boundary、未知类型或需要用户手工删除的行。

### REQ-015 实现生成前校验与 MOOSE 输入预检（P0）

- 目标/价值：在提交计算节点前发现几何、绑定、物理和语法问题，避免把必然失败的任务送入队列。
- 业务规则：
  - 结构校验至少覆盖：活动网格存在且未过期、物理组有效、材料已指派、变量与方程完整、BC/Load/Contact 选择集存在、Step/Executioner 完整、输出变量受支持、所有引用对象可解析。
  - 语义校验至少覆盖：区域维度匹配、重复或冲突约束、未使用对象、单位/量纲提示、应用不支持的类型、多个 Step 的处理策略、网格维度与物理维度一致。
  - `.i` 生成后先进行内部语法/映射校验；目标 MOOSE 可执行程序可用时自动执行 `--check-input`，远程模式应支持在计算节点或校验服务执行同等预检。
  - 校验结果按错误、警告、提示分级；错误阻止提交，警告需要用户确认或显式豁免，点击问题可跳转到对应树节点和表单字段。
  - “Workflow ready” 必须表示 `.i + mesh` 已通过所有阻断校验，而不是仅表示每类节点数量大于零。
- 数据/接口影响：校验结果与生成产物版本关联；上游修改后旧校验结果立即失效。
- 关联逻辑/路径：`src/PropertyEditor.cpp` Validation Summary、`src/MoosePanel.cpp::on_check_input()`、`MainWindow::refresh_workflow_status()`。
- 验收标准：删除材料指派、重命名 Physical Group、破坏网格路径或使用不支持的 Contact 类型时，系统均在提交前拦截并给出可定位说明；合法案例通过 `--check-input`。

### REQ-016 生成可复现的计算案例包（P0）

- 目标/价值：把前处理结果冻结为作业系统可以完整上传、校验和重跑的输入快照。
- 业务规则：
  - 常规案例包至少包含主 `.i`、其引用的 `.msh`、必要 extra files 和 `manifest.json`；可选包含只读项目快照、生成报告和 Physical Groups 清单。只有显式导入 Exodus 网格或多阶段初始化时才允许 `.e` 作为输入。
  - manifest 记录项目/案例标识、输入文件名与 SHA-256、网格/附件列表与哈希、模板/映射版本、生成时间、目标求解程序和推荐命令，并给每个文件标记 `input_mesh`、`input_config`、`result`、`initial_state` 或 `restart_data` 等角色。
  - manifest 同时记录应用档案/版本、求解单位合同、显示到求解单位的比例因子、生成器版本、基础模型/专家扩展/最终 `.i` 哈希及 `input_mode`。
  - `.i` 内的所有相对文件引用在案例包根目录下可解析；不得引用只存在于建模机绝对路径中的文件。
  - 案例包一经提交即不可被后续 UI 编辑原地修改；再次生成形成新快照或新版本。
  - UI 支持查看“当前项目状态 → 输入快照 → 作业 ID → 结果文件”的追溯关系。
- 数据/接口影响：沿用现有 `input_snapshot`/manifest 合同并补齐网格与生成来源元数据。
- 关联逻辑/路径：`src/MoosePanel.cpp` 快照导出、`src/SimClient.cpp`、`include/gmp/SimClient.h`、`ArtifactDialog`。
- 验收标准：将案例包复制到具备对应 MOOSE 应用的干净计算目录后，可使用 manifest 中的命令运行，且不依赖原项目路径。

### REQ-017 与现有作业系统形成提交和结果闭环（P0）

- 目标/价值：复用已经搭建的作业系统，把 UI 前处理产物可靠提交到计算节点，并把状态和结果带回项目。
- 业务规则：
  - 标准操作链为“生成网格 → 装配 `.i` → 校验 → 创建不可变快照 → 提交作业”；允许分步执行，也提供在所有前置条件满足时的一键入口。
  - 远程提交直接上传 `.i`、网格和附件，不应要求建模机本地存在 MOOSE 可执行程序；本地/WSL 运行继续使用现有 Runner。
  - 提交后在 Jobs 节点显示排队、运行、成功、失败、取消等状态，记录输入快照版本、计算节点/队列、并行配置、开始/结束时间和日志入口。
  - 失败时保留生成报告、预检结果、标准输出和标准错误；重试默认复用原不可变快照，修改模型后应创建新快照再提交。
  - 作业完成后自动登记 Exodus/CSV/日志等 Results 节点，并可从结果追溯到 Job、`.i`、网格和项目版本。
- 数据/接口影响：保持现有 LIMS Facade/SimClient 提交合同兼容，新增字段应版本化且向后兼容。
- 关联逻辑/路径：`MainWindow::start_submit_workflow()`、`src/MoosePanel.cpp::on_submit_job()`、`src/SimClient.cpp`、Jobs/Results 模型树节点。
- 验收标准：参考案例通过 UI 生成并校验后可提交到计算节点；作业状态、日志和结果文件回写项目，用户无需手工复制 `.i` 或 `.msh`。

## 4. 关键交互流程

### 4.1 编辑已有节点

1. 用户在左侧模型树单击可编辑子节点。
2. 树节点高亮，中央舞台同步高亮对应对象，工作上下文条切换到节点所属模块和对象。
3. 用户双击该节点或执行“编辑”命令，在舞台内打开对应的模态编辑弹窗；窗口打开期间保持活动对象不变。
4. 用户修改字段；未应用修改只存在于编辑缓冲。
5. 点击“确定”后校验、写回模型树、标记项目已修改并关闭；点击“取消”后放弃本次全部改动。

### 4.2 拖拽常用工具组到舞台右上角

1. 用户按住工具组拖拽手柄。
2. 离开顶部停靠区后，工具组变为浮动窗口，舞台拾取暂时禁用。
3. 靠近舞台右上角预置位置时显示磁吸轮廓。
4. 释放后工具组对齐到右上角，舞台恢复交互，布局状态持久化。
5. 用户可将其拖回顶部/侧边，或通过 View 菜单隐藏并再次恢复。

### 4.3 切换 Sketch 与普通 3D 模块

1. 进入 Sketch 模块时，保留当前选中草图并切换舞台为 2D 编辑模式。
2. 舞台左侧工具栏显示草图绘制/约束组，通用视图组保留适用于 2D 的命令。
3. 离开 Sketch 时先处理未保存草图状态，再恢复 3D 相机和通用工具组。
4. 若节点编辑弹窗仍打开，则先要求用户确定或取消；弹窗关闭后再完成模块切换，不得把草图参数错误写入其他节点。

### 4.4 通过工作上下文条切换模块和对象

1. 用户在“模块”选择器中切换到 Material、Mesh、Job 等目标模块。
2. 顶部模块命令组和舞台左侧工具组同步刷新；左侧导航切换到适合该模块的树视图，但不丢失项目数据。
3. “当前模型/项目”显示命令的数据归属；单模型阶段保持只读。
4. “当前对象”列出当前模块可操作的同类对象；选择对象后，左树定位该节点，舞台同步高亮。
5. 用户从模型树选择其他对象时，工作上下文条反向更新，不需要重复手动选择。

### 4.5 从 Gmsh 几何生成 MOOSE 案例并提交作业

1. 用户创建/导入几何，完成部件和装配定位；在舞台选择体、面、线或点并建立命名 Physical Groups。
2. 用户选择 MOOSE 应用/物理配置，创建变量、材料和 Section 指派，补充 Step/求解控制、接触/约束、BC/Load 和输出对象。
3. 系统运行依赖校验；缺少材料指派、物理方程、选择集或应用映射时，Workflow 显示阻断项并导航到对应对象。
4. 用户生成 Gmsh `.msh`；系统记录物理组和网格摘要，并将网格版本与当前几何/装配状态绑定。
5. 用户执行“生成 MOOSE 输入”；装配器使用 `.msh`、物理组、模型对象和应用模板生成 `case.i`，同时展示来源追踪和生成报告。
6. 系统执行内部校验及可用的 MOOSE `--check-input`；通过后将状态标记为“可提交”。
7. 用户创建计算快照，系统写出 `.i + .msh + extra files + manifest.json` 并冻结版本。
8. 用户通过现有作业系统提交到计算节点；Jobs 节点持续显示状态、进度和日志。
9. 计算完成后，结果文件自动登记到 Results，用户在 Visualization/Plot/Table 中查看，并能追溯到对应输入快照。

## 5. 非功能性需求

- 性能：常规树节点的浮动表单应在用户操作后 200 ms 内出现或完成刷新；工具组拖动保持连续，不因重建 VTK 管线产生明显停顿。中等规模项目的 `.i` 内部装配和结构校验目标在 1 秒内完成，Gmsh 网格和外部 `--check-input` 单独显示进度且支持取消。
- 稳定性：关闭浮窗、切换模块、恢复布局和切换语言不得导致崩溃、悬空指针或丢失未提示的编辑内容。
- 可用性：主要命令可通过菜单、快捷键或可见工具按钮到达；图标按钮均有 Tooltip；危险操作继续二次确认。
- 可访问性：键盘可遍历菜单、工具栏、树和表单；焦点状态清晰；状态表达不只依赖红/绿色。
- 适配：重点支持 1280×720 及以上窗口、100%～200% DPI、多屏和屏幕热插拔；浮动窗口始终可找回。
- 可观察性：布局恢复失败、表单校验失败和任务执行结果通过状态栏/消息区记录，必要时写入现有调试日志。
- 国际化：新增菜单、工具提示、弹窗标题和校验信息必须进入现有 L10n 字典，不在业务代码中只提供单一语言。
- 确定性：相同项目状态、网格和映射版本必须生成等价且顺序稳定的 `.i` 和 manifest；生成器不得依赖控件遍历顺序或本机绝对路径。
- 可追溯性：模型对象、Physical Groups、生成 blocks、输入快照、Job 和 Results 之间保留可查询关联。
- 安全：案例包文件名、相对路径和远程命令参数必须经过白名单/规范化处理；生成器不得把任意 UI 文本拼接成未经验证的执行命令。

## 8. 风险与假设

### 8.1 风险

- `PropertyEditor` 当前在字段变化时即时写回节点，引入“应用/取消”语义需要编辑副本，否则取消无法可靠回滚。
- `property_stack_` 同时承载属性页和多个业务模块，直接删除右栏会让 Mesh、Job、Visualization 等复杂页面失去父容器，必须先完成承载迁移。
- `VtkViewer::control_tabs()` 和 `top_bar()` 当前被重新设置父控件到 Visualization 右栏，迁回舞台时需避免重复归属、生命周期和信号连接问题。
- 浮动工具组覆盖 VTK 窗口时可能与拾取、橡胶筋选择和高 DPI 坐标换算冲突。
- Qt 原生浮动工具栏在 macOS、Windows、Linux 的窗口行为存在差异，需要统一越界恢复和布局序列化策略。
- 当前 `sync_model_to_input()` 只装配 7 类 blocks，并把 Loads 统一当作 Kernels、只使用第一个 Step；直接扩充字符串拼接会产生错误但外观完整的 `.i`。
- `ensure_basic_workflow_nodes()` 当前会自动补齐占位 Part/Material/Section/BC/Load；数量齐全不等于物理模型可运行，重构后不能用占位对象绕过 readiness 校验。
- 当前通用 BC 注入会生成 `variable = u`、`value = 0` 的默认 DirichletBC，只适合演示，不能作为真实前处理映射策略。
- Abaqus 与 MOOSE 的物理对象不是一一对应；Section、Step、Contact、Coupling、Field/History Output 必须按目标应用解释，映射范围失控会显著扩大实施成本。
- Gmsh 拓扑 tag 在布尔、重建和装配后可能变化；若 Physical Groups 只保存 tag，材料、接触和边界绑定会失效。
- 不同 MOOSE 应用和版本的对象类型/参数可能变化，映射注册表必须版本化并配套验证样例。
- 当前 Sketch/OCC 几何以 mm 为内部约定，而首批官方应用档案使用 SI 求解合同；若量纲化数据迁移或显式转换链不完整，结果可能数值错误但输入检查仍通过。

### 8.2 假设

- “与 Abaqus 一致”指信息架构、操作层级和工程软件交互习惯一致，不要求像素级复制其皮肤和图标。
- “可拖拽到任何位置”指可在主窗口各停靠边和舞台可视范围内浮动；不要求工具组脱离应用后跨桌面任意停放。
- 默认按工作上下文条中的紧凑模块选择器替换当前整行模块页签，以释放顶部空间；业务模块名称和能力保持不变。
- 当前目标基线按 Abaqus 参考采用模态节点编辑弹窗和“确定/取消”提交语义；日志、结果详情等查看窗口可采用非模态方式。
- 底部消息/作业区保留，但默认高度应明显小于当前 Console 展开状态，并允许折叠。
- 最终产物是 MOOSE `.i`，不是 Abaqus `.inp`；Abaqus 流程只作为前处理阶段和交互对标。
- `.geo` 不直接嵌入 `.i`；Gmsh 先生成 `.msh`，`.i` 通过 FileMesh 引用网格并使用命名物理组完成计算信息绑定。
- 每个可提交案例都明确选择目标 MOOSE 应用/可执行程序和匹配的映射模板；不存在脱离应用语义的“万能 `.i`”。
- 现有作业系统、快照 manifest 和 SimClient 是本次提交闭环的基础，新增元数据在其合同上向后兼容扩展。

## 9. 关键决策记录（已确认）

1. 属性表单交互
   - 决策：已确认采用 Abaqus 风格的事务式模态编辑。
   - 交互规则：单击树节点只选择、定位并更新工作上下文；双击节点或执行“编辑”命令后打开模态弹窗。
   - 提交规则：弹窗使用编辑副本；“确定”在校验通过后一次性写回，“取消”、关闭按钮和 `Esc` 均丢弃本次未提交修改。
   - 新建规则：新对象仅在“确定”后插入模型树，不保留取消创建产生的半成品节点。
   - 例外规则：材料预览、显示参数等确需连续观察结果的表单可增加“应用”，应用后保持弹窗打开；查看类窗口仍可非模态。
2. Job/Results 复杂页面承载方式
   - 决策：已确认采用独立工作窗；中央 3D 舞台始终显示，不被 Job、Results、Plot 或 Table 页面替换。
   - 承载规则：Job 列表、详情和管理操作进入独立 Job 工作窗；Results 列表、筛选、Plot/Table 和详情进入独立 Results 工作窗；三维结果仍加载到中央舞台。
   - 辅助规则：顶部可保留高频运行/停止命令，底部消息区保留紧凑作业状态和日志摘要，但不得扩展成替代中央舞台的常驻工作页。
   - 窗口规则：Job 和 Results 各使用一个可复用的非模态单实例工作窗；重复执行入口命令时激活已有窗口，不重复创建。
   - 状态规则：两个工作窗分别记忆尺寸、位置、筛选条件和内部栏宽；屏幕变化或位置越界时自动移回可用屏幕，允许用户将其拖到第二块屏幕。
   - 关闭规则：关闭工作窗只关闭界面，不停止作业，也不卸载已经加载到中央舞台的结果。
   - 多窗口例外：Results 仅在用户显式执行“新建对比窗口”时允许创建额外窗口；Job 管理窗不提供多实例。
   - 模态边界：Job/Results 工作窗本身不阻塞主界面；创建或编辑 Job 参数仍使用事务式模态弹窗。
3. Material Library 页签范围
   - 决策：已确认本期不加入独立 Material Library 页签，只保留 Model/Results 导航和项目内 `Materials` 节点。
   - TODO：后续材料库具备跨项目持久化与检索、单位/本构/适用 MOOSE 应用及版本元数据、版本与来源追踪、导入导出、复制到当前项目，以及共享材料快照或显式升级机制后，再启用独立页签。
   - 约束：本期不得显示无内容、无复用闭环的占位页签；现有 `GMP_MOOSE_TEMPLATES` 完整输入模板库不能冒充材料库。
4. MOOSE 应用选择与首期物理场
   - 决策：已确认不得将产品锁定到单一 MOOSE 应用；必须支持选择应用配置，以便后续切换和扩展。
   - 应用档案：每个可选应用配置至少声明应用标识、可执行程序、版本/提交号、计算节点环境、支持的物理场与对象类型、`.i` 映射注册表、校验命令和兼容性级别。
   - 初始配置：可将 `DamSafetyApp-opt`、`blackbear-opt`、`combined-opt` 等现有目标注册为不同应用档案，但只有完成能力验证的档案才能标记为“可提交”；开发或 prototype 档案必须明确标识。
   - 生成规则：界面、可用节点类型、表单字段、`.i` 生成和 `--check-input` 均由当前应用档案驱动；切换应用后不得继续静默使用原应用专属对象。
   - 物理场基线：首期优先打通三维小应变准静态固体力学与位移控制；高级混凝土、接触和耦合的真实运行范围在下一项确认。
   - 选择范围：采用项目级活动应用档案；顶部工作上下文提供选择入口，一个项目同一时刻只有一个活动档案。
   - 切换规则：切换前生成兼容性报告，区分可直接复用、可自动迁移、需人工配置和目标应用不支持的对象；切换不删除原参数，不兼容对象标记为“未映射/阻断”。
   - 迁移规则：提供“复制项目并切换应用”入口，用于比较不同应用并保留原项目；不得在无提示情况下自动改写物理语义。
   - Job 规则：每次 Job 固化应用标识、版本、映射版本、计算节点环境和 `.i` 快照；历史 Job 不随项目后续切换改变。Job 只能选择活动档案允许的节点/可执行版本，不得临时用另一应用重新解释模型。
5. Word 参考案例高级能力的真实运行范围
   - 决策：已确认采用分阶段真实运行方案；最终验收要求 CDP/认可的损伤塑性模型、摩擦接触和参考点耦合全部真实运行，任何阶段都不得以 UI 假实现或不可执行伪 block 代替。
   - 里程碑 1：实现三维混凝土块与钢板、已验证的线弹性材料、可配置摩擦面—面接触、底面固定、直接施加于钢板加载面的位移，以及位移/应力/应变/接触量/反力输出；生成 `.i` 必须通过目标应用检查并完成一次计算。
   - 里程碑 2：实现参考点和运动耦合的真实 MOOSE 映射，验证位移和合力传递；不得用“整面统一位移”静默冒充参考点耦合。
   - 里程碑 3：接入并验证 CDP 或所选应用认可的混凝土损伤塑性模型，完成参数来源追踪、单位检查和基准对比，达到 Word 参考案例完整真实运行。
   - 支持分级：只有“已支持”对象可正常生成和提交；prototype 必须显著标识且默认不可用于正式作业；不支持能力保持禁用并解释原因。
6. `.msh`、`.i` 与 `.e` 的文件角色
   - 决策：已确认常规流程固定为 `.msh + .i → .e`；不默认把 `.msh` 转换为 `.e`。
   - 常规角色：`.msh` 是 Gmsh 生成的输入网格，`.i` 是 MOOSE 计算配置，`.e` 是 MOOSE 产生的 Exodus 计算结果。
   - `.i` 规则：新建项目生成的 `.i` 默认通过相对路径引用快照内的 `.msh`，并使用命名 Physical Groups 绑定 block/boundary。
   - `.e` 输入例外：只有用户显式执行“导入已有 Exodus 网格”，或多阶段分析需要从上一阶段结果初始化网格/变量时，才允许 `.e` 作为输入；不得把普通结果文件自动解释为完整重启状态。
   - 多阶段约束：继承哪些变量、材料内部状态和求解状态必须由应用档案明确声明并校验；完整续算需要的 checkpoint/restart 附件必须一并进入快照。
   - manifest 规则：每个文件标记 `input_mesh`、`input_config`、`result`、`initial_state` 或 `restart_data` 等角色，避免同为 `.e` 时混淆输入和输出。
7. 单位系统约定
   - 决策：已确认单位不由 MOOSE 全局强制规定，而由当前应用档案声明求解单位合同；首批官方应用档案采用 SI，UI 显示单位与求解单位分离。
   - 框架事实：MOOSE 和 Abaqus 通常要求用户保证单位自洽，不会自动识别 `150` 表示 mm 还是 m；个别材料模型或经验公式声明的特定单位要求优先于通用自洽原则。
   - 初始求解合同：首批官方 DamSafetyApp/BlackBear 档案使用 `m、N、s、kg、Pa`；其他应用可注册不同但完整自洽的单位合同，不得把 SI 写成产品级永久限制。
   - 显示规则：结构工程 UI 默认显示 mm、MPa、N/kN 和 s；字段始终显示单位，并把数值按当前应用档案显式转换为求解值。
   - 导入规则：CAD/网格导入必须选择或确认源长度单位；无法确定时不得静默猜测。生成报告和 manifest 记录源单位、求解单位、比例因子及转换版本。
   - 切换规则：切换应用档案时按物理量量纲生成单位兼容性与转换报告；无法识别量纲的高级参数不自动转换，必须阻止切换或要求人工确认。
   - 数据要求：物理量逐步从无单位字符串迁移为“数值 + 量纲 + 单位”；`.e` 结果按其应用档案的求解单位解释，再转换为项目显示单位。
8. 系统生成 `.i` 的编辑策略
   - 决策：已确认采用“普通模式只读 + 专家受控扩展 + 显式脱离的完全手工模式”。
   - 普通模式：模型树和结构化表单是单一事实来源；系统生成 `.i` 只读，提供预览、搜索、语法高亮和来源定位，随模型变更重新生成。
   - 专家扩展模式：通过 `Custom MOOSE Objects / Custom Blocks` 扩展节点写入应用档案允许的位置；系统生成区与用户扩展层分开保存，合并时执行名称冲突、引用和对象支持校验，并显示来源及差异。
   - 完全手工模式：用户显式执行“转为手工维护 `.i`”后生成独立副本，该文件不再与模型树自动同步；原结构化模型继续保留，返回结构化模式时生成新文件并展示差异，不覆盖手工文件。
   - 提交规则：专家扩展必须通过目标应用检查；完全手工文件在快照中标记 `input_mode = manual`，能否正式提交由应用档案或项目权限控制。
   - 追踪规则：快照记录生成器版本、基础模型哈希、扩展层哈希和最终 `.i` 哈希；禁止直接修改系统生成区后又静默重新生成。
